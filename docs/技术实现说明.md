# 黑马点评项目技术实现说明

本文档用于面试前复习代码，不作为主项目说明书。重点说明关键代码文件的职责、设计流程和这样设计的好处。

## 1. 项目分层结构

```text
com.hmdp
├── controller     对外 REST 接口
├── service        业务接口
├── service.impl   业务实现
├── mapper         MyBatis-Plus 数据访问层
├── entity         数据库实体
├── dto            接口返回对象和数据传输对象
├── config         Redis、RabbitMQ、Redisson、Sentinel、拦截器等配置
├── utils          缓存、锁、ID、登录上下文等通用工具
├── listener       RabbitMQ 消费者
├── handler        Canal binlog 消费处理
├── ai             DeepSeek 客服编排与业务工具
└── amap           高德 POI 周边搜索客户端
```

## 2. 秒杀核心代码

### 2.1 `VoucherOrderController.java`

位置：`src/main/java/com/hmdp/controller/VoucherOrderController.java`

作用：

- 暴露秒杀接口：`POST /voucher-order/seckill/{id}`。
- 使用 `@SentinelResource` 标记 Sentinel 资源。
- 将请求转交给 `IVoucherOrderService.seckillVoucher(voucherId)`。

设计好处：

- Controller 保持很薄，只负责入口和流控标记。
- 业务逻辑集中在 Service，便于维护和测试。

### 2.2 `VoucherOrderServiceImpl.java`

位置：`src/main/java/com/hmdp/service/impl/VoucherOrderServiceImpl.java`

核心方法：

- `seckillVoucher(Long voucherId)`
- `createVoucherOrder(VoucherOrder voucherOrder)`

请求线程内的流程：

1. 检查 Caffeine 售罄缓存。
2. 获取当前登录用户 ID。
3. 使用 `RedisIdWorker` 生成订单 ID。
4. 执行 `seckill.lua`。
5. 根据 Lua 返回值判断库存不足、重复下单或成功。
6. 成功后发送订单消息到 RabbitMQ。
7. 立即返回订单 ID。

消费者线程内的流程：

1. 对 `lock:order:{userId}` 加 Redisson 锁。
2. 查询 MySQL 是否已有同一用户同一券订单。
3. 执行 MySQL 乐观扣减：`stock = stock - 1` 且 `stock > 0`。
4. 保存订单。
5. 捕获 `DuplicateKeyException`，由唯一索引兜底。
6. 释放锁。

设计好处：

- 请求线程不直接写库，响应更快。
- Redis Lua 承担高并发前置校验。
- MQ 消费端负责最终落库。
- 多层兜底降低超卖和重复下单风险。

### 2.3 `seckill.lua`

位置：`src/main/resources/seckill.lua`

作用：

- Redis 内原子完成秒杀资格判断。

逻辑：

1. `GET seckill:stock:{voucherId}` 判断库存。
2. `SISMEMBER seckill:order:{voucherId} userId` 判断用户是否下单。
3. `INCRBY seckill:stock:{voucherId} -1` 预扣 Redis 库存。
4. `SADD seckill:order:{voucherId} userId` 记录下单用户。
5. 返回 `0` 表示成功，`1` 表示库存不足，`2` 表示重复下单。

设计好处：

- 多个 Redis 操作合并到一个脚本内执行。
- 避免库存判断和扣减之间出现并发插入。
- 降低请求进入 MySQL 的数量。

### 2.4 `RedisIdWorker.java`

位置：`src/main/java/com/hmdp/utils/RedisIdWorker.java`

作用：

- 生成全局唯一订单 ID。
- 通常由时间戳 + Redis 自增序列组合。

设计好处：

- 避免数据库自增 ID 在高并发下成为瓶颈。
- 订单 ID 可在请求线程中提前生成，用于 MQ 消息传递。

## 3. RabbitMQ 异步削峰代码

### 3.1 `MqConfig.java`

位置：`src/main/java/com/hmdp/config/MqConfig.java`

作用：

- 定义秒杀交换机：`seckill.exchange`。
- 定义秒杀主队列：`seckill.queue`。
- 定义死信交换机：`seckill.dlx`。
- 定义死信队列：`seckill.dlq`。
- 配置 JSON 消息转换器。
- 配置 RabbitTemplate confirm 和 returns 回调。
- 配置消费者并发参数。

关键配置：

```yaml
seckill:
  mq:
    concurrent-consumers: 4
    max-concurrent-consumers: 8
    prefetch: 20
```

设计好处：

- 主队列负责订单削峰。
- 死信队列负责异常消息兜底观察。
- 消费者并发和 prefetch 可配置，便于压测调优。

### 3.2 `MqMessageListener.java`

位置：`src/main/java/com/hmdp/listener/MqMessageListener.java`

作用：

- 监听 `seckill.queue`。
- 收到 `VoucherOrder` 消息后调用 `voucherOrderService.createVoucherOrder()`。

设计好处：

- 消费逻辑简单，业务处理仍在 Service 层。
- MQ 与业务解耦，后续可扩展重试、补偿、监控。

## 4. 防超卖与一人一单兜底

### 4.1 Redis 层

文件：

- `seckill.lua`
- `VoucherOrderServiceImpl.java`

作用：

- Redis 库存先扣减。
- 用户下单集合先写入。

好处：

- 大部分无效请求在 Redis 层被拦截。

### 4.2 应用层

文件：

- `VoucherOrderServiceImpl.java`
- `RedissonConfig.java`

作用：

- 消费端使用 `lock:order:{userId}` 控制同一用户并发落库。

好处：

- 防止同一用户并发消息重复落库。

### 4.3 数据库层

文件：

- `src/main/resources/db/hmdp.sql`

关键设计：

```sql
UNIQUE INDEX uk_user_voucher(user_id, voucher_id)
```

作用：

- 数据库最终保证同一用户同一优惠券只能有一条订单。

好处：

- 即使 Redis 或应用层出现极端边界，数据库仍能兜底。

## 5. 缓存相关代码

### 5.1 `CacheClient.java`

位置：`src/main/java/com/hmdp/utils/CacheClient.java`

支持能力：

- 普通缓存写入。
- 空值缓存，解决缓存穿透。
- 互斥锁缓存重建。
- 逻辑过期缓存重建。

设计好处：

- 将缓存通用逻辑抽离，Service 层不需要重复写缓存模板代码。
- 针对不同场景可选择不同缓存策略。

### 5.2 `ShopServiceImpl.java`

位置：`src/main/java/com/hmdp/service/impl/ShopServiceImpl.java`

作用：

- 商铺详情查询走 Redis 缓存。
- 商铺更新后删除缓存，保证下次读取重新加载。
- 根据分类和坐标查询附近店铺，优先 Redis GEO，不足时回退数据库并计算距离。

设计好处：

- 热点商铺详情不频繁访问数据库。
- 附近查询更贴近本地生活业务场景。

### 5.3 `LocalCacheConfig.java`

位置：`src/main/java/com/hmdp/config/LocalCacheConfig.java`

作用：

- 配置 Caffeine 本地缓存。
- `stockSoldOutCache` 缓存秒杀券售罄状态。
- `hotDataCache` 预留热点数据缓存。

设计好处：

- 对库存已售罄的请求，短时间内直接在 JVM 内返回，减少 Redis 压力。

## 6. 用户登录与拦截器

### 6.1 `UserServiceImpl.java`

位置：`src/main/java/com/hmdp/service/impl/UserServiceImpl.java`

作用：

- 发送验证码。
- 登录或注册用户。
- 生成 Access Token 和 Refresh Token。
- 将用户信息写入 Redis。
- 使用 Bitmap 处理签到。

设计好处：

- 登录态不依赖 Tomcat Session，适合分布式部署。
- Redis Bitmap 存签到节省空间。

### 6.2 `RefreshTokenInterceptor.java`

作用：

- 从请求头读取 token。
- 从 Redis 获取用户信息。
- 刷新 token 有效期。
- 将用户保存到 `UserHolder`。

### 6.3 `LoginInterceptor.java`

作用：

- 对需要登录的接口做统一鉴权。
- 未登录则拦截。

设计好处：

- 业务代码不用重复判断登录。
- 当前用户信息通过 ThreadLocal 获取，使用方便。

## 8. Sentinel 限流代码

### 8.1 `SentinelConfig.java`

作用：

- 注册 Sentinel AOP 切面。
- 初始化 `seckillController` 的 QPS 规则。

当前配置：

```java
controllerRule.setCount(10000);
```

说明：

- 当前阈值较大，主要用于测试 TPS 极限，不让 Sentinel 过早拦截。
- 如果上线或演示保护效果，可以降低到符合本机承载能力的数值。

### 8.2 `SentinelFallback.java`

作用：

- 定义被 Sentinel 拦截或系统异常时的返回结果。

好处：

- 高峰期可以快速失败，避免服务被拖垮。

## 9. Canal 相关代码

### 9.1 `CanalClientConfig.java`

作用：

- 从配置读取 Canal host、port、destination、filter、enabled。
- 创建 `CanalStockHandler`。

### 9.2 `CanalStockHandler.java`

作用：

- 连接 Canal Server。
- 订阅 `hmdp.tb_seckill_voucher` 和 `hmdp.tb_voucher_order`。
- 监听库存变化，同步 `seckill:stock:{voucherId}`。
- 监听订单插入，同步 `seckill:order:{voucherId}`。

当前状态：

```yaml
canal:
  enabled: false
```

设计好处：

- 作为后续增强能力，可以减少缓存与数据库之间的不一致窗口。
- 但需要完整部署 MySQL binlog 和 Canal Server，当前压测不依赖它。

## 10. AI 客服与地图代码

### 10.1 `AiCustomerController.java`

作用：

- 提供 AI 客服接口。
- 接收用户问题、经纬度、城市等参数。
- 调用 `CustomerServiceOrchestrator`。

### 10.2 `CustomerServiceOrchestrator.java`

作用：

- 判断用户问题意图。
- 决定调用订单查询、库存查询、店铺查询、附近推荐等工具。
- 拼接业务上下文后请求 DeepSeek。
- DeepSeek 不可用时返回本地兜底文案。

设计好处：

- 大模型不直接凭空回答，而是基于业务数据回答。
- 降低 AI 编造店铺、订单、库存的概率。

### 10.3 `CustomerServiceTool.java`

作用：

- 封装 AI 可用的业务查询能力。
- 包括订单查询、优惠券库存、店铺优惠券、附近店铺、店铺详情等。

### 10.4 `AmapPoiClient.java`

作用：

- 调用高德 Web 服务 POI 周边搜索。
- 按经纬度、半径、关键词查询附近真实店铺。
- 结果写入 Redis 缓存。

设计好处：

- 弥补本地数据库店铺数据少、城市覆盖不足的问题。
- 通过缓存减少外部 API 调用次数。

## 11. 压测复盘

### 11.1 主压测

推荐采用 2500 并发作为稳定成果：

```text
2500 并发，库存 100，异常率 0%，吞吐量约 893.5 TPS，
平均响应 12ms，P95 29ms，P99 65ms。
```

压测后校验：

```text
订单数 = 100
MySQL stock = 0
Redis stock = 0
Redis order set = 100
重复 user_id 查询为空
RabbitMQ 主队列无积压
RabbitMQ 死信队列为 0
```

### 11.2 3000 并发边界

3000 并发出现连接拒绝，异常率约 44.27%。这说明本机运行环境在该并发附近出现连接承载瓶颈。因为不是业务失败，所以不建议把 3000 作为稳定成果。

### 11.3 面试表达建议

可以说：

> 我没有只看 JMeter 吞吐量，而是每轮压测后同时检查 MySQL 订单数、MySQL 库存、Redis 库存、Redis 下单用户集合、RabbitMQ 主队列和死信队列。最终选择 2500 并发这组异常率为 0 的数据作为稳定结果，3000 并发虽然数据一致性仍正确，但出现连接拒绝，因此只作为本机边界观察。

这种说法比单纯报一个 TPS 更可信。
